# SharePoint Folder Structure Designer

## Purpose

ReadyPackets administrators can configure the phase-relative SharePoint folders created when an order enters a configured Phase Kickoff stage. The designer is available in **Admin → Integrations → Phase Kickoff**. It allows the Phase I, Phase II, In Production, and Delivered structures to be edited without source-code changes.

> The designer changes only the **phase-relative folder structure**. It does not change the ReadyPackets customer or order identity hierarchy, and it never moves or deletes an existing SharePoint folder.

## Managed folder hierarchy

The SharePoint base folder is set separately in **Admin → Integrations → SharePoint & SAML**. Under that approved base, ReadyPackets creates the following managed hierarchy:

```text
{base}/customers/{customerId}/orders/{orderNumber}/
```

The `customerId` and `orderNumber` segments are generated by ReadyPackets so that records remain opaque, attributable, and collision-safe. The folder structure designer appends each configured relative path below that order root.

| Example base folder | Configured Phase I path | Resulting folder preview |
|---|---|---|
| `ReadyPackets/Orders` | `Phase I/Docs` | `ReadyPackets/Orders/customers/{customerId}/orders/{orderNumber}/Phase I/Docs` |
| `Client Work/ReadyPackets` | `Phase I/Audio` | `Client Work/ReadyPackets/customers/{customerId}/orders/{orderNumber}/Phase I/Audio` |

## Editing a phase template

Open the relevant Phase Kickoff card, add, remove, or modify the listed relative paths, then select **Save structure**. Each template accepts up to 32 paths. A path may use letters, numbers, spaces, underscores, parentheses, periods, hyphens, and nested `/` separators.

The server normalizes accidental leading/trailing separators and blocks traversal segments such as `..`, unsupported SharePoint path characters, blank folders, and duplicate paths regardless of letter case. The server records the administrative change in the ReadyPackets activity log.

Use **Restore default** to discard the custom template for that phase and return to the built-in ReadyPackets folder structure.

| Phase | Default folders |
|---|---|
| Phase I — Intake | `Phase I/audio`, `Phase I/Docs`, `Phase I/Final_Merge`, `Phase I/Results` |
| Phase II — Synthesis | `Phase II/Audio`, `Phase II/Docs`, `Phase II/Final_Merge`, `Phase II/Results` |
| In Production | `Phase III/Branches`, `Phase III/Context`, `Phase III/Final_Internal`, `Phase III/Run_Logs` |
| Delivered | `Phase IV/Client_Facing`, `Phase IV/Final_Delivery`, `Phase IV/Internal_Audit`, `Phase IV/Results` |

## Effect on SharePoint synchronization

The configured structure is applied when a future Phase Kickoff folder job runs. Folder creation is idempotent: ReadyPackets checks for a SharePoint segment before creating it, so repeated jobs do not create duplicate folders.

Changes do **not** rename, move, or delete folders already present in SharePoint. They also do not rewrite historical SharePoint sync logs. If an order has not yet reached a phase, its future phase job uses the current template. If a folder already exists, it remains in place.

Document and audio synchronization may be routed to a specific folder by the applicable **Order Workflow** stage’s SharePoint document or audio destination. Those workflow-stage routing settings take precedence for file delivery; the Phase Kickoff designer controls the broader folder creation layout.

## Recommended operating procedure

Create the desired design in a test order first. Confirm that the base folder, customer/order hierarchy, phase paths, document route, audio route, and SharePoint sync log all match expectations. Then save the production phase template and allow the next normal phase kickoff to create missing folders. Avoid manually moving active order folders in SharePoint, because ReadyPackets retains its audited sync paths and will not infer a manual relocation.
