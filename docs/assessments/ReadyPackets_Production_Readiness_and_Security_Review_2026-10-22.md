## 1. Executive decision summary

The reviewed revision has a thoughtful baseline in several areas: server-side browser-session validation, strong cookie flags, Argon2id password handling, encrypted sensitive fields, a nonce-based CSP, guarded tRPC procedures, deployment hardening for the main application service, and useful backup/restore scaffolding. The review tracks also recorded successful static type/lint checks and focused test suites. These are meaningful foundations, not evidence of an approved internet-facing production posture.

The current release is blocked principally by high-impact weaknesses in:

1. **Identity and delegated authorization** — SAML response correlation/issuer binding, MFA-factor replacement, native-token revocation, and scope enforcement for shared orders.
2. **Financial and workflow integrity** — Stripe payment-state validation/idempotency, coupon concurrency, payment-status authority, and order-creation idempotency.
3. **Data protection and recovery** — plaintext-by-default full backups containing recovery material, non-atomic cross-store backup snapshots, orphaned upload/SharePoint data, and pre-release file-malware controls.
4. **Internet edge and operational assurance** — potentially spoofable Cloudflare client identity when the origin is reachable, an installer that can finish without working public TLS, mutable release inputs, and missing independently retained audit/alert evidence.
5. **Availability and release governance** — restore false-success paths, no evidenced RPO/RTO drill, no implemented HA/multi-region deployment, and insufficient enforceable CI supply-chain controls.

## 2. Scope, evidence discipline, and limitations

### Scope

This report consolidates the supplied specialist review tracks for the exact revision named above. It covers application code, tracked deployment scripts/configuration, migrations/schema, CI workflows, selected tests, and operational documentation. No repository source was changed for this review.

### Evidence labels used in this report

| Label | Meaning |
|---|---|
| **C — code/configuration confirmed** | The behavior or missing control was observed in the cited reviewed source/configuration at the reviewed revision. |
| **O — operational verification required** | The condition, control effectiveness, or deployment state cannot be established from the repository and must be evidenced in staging/production. |
| **C/O — conditional exposure** | Source establishes a behavior; exploitation or reachability depends on a stated deployment condition, such as SAML enablement, Cloudflare use, an administrator IP allowlist, or use of S3. |

### Important limitations

- This was a bounded static review. No production/staging host, database, object store, SharePoint tenant, Stripe account, IdP, CDN/WAF, DNS zone, certificate, secret, backup artifact, collector, or cloud firewall was accessed or altered.
- The review did not execute migrations, start the application, conduct an external scan, perform a restore, submit an IdP assertion, send payment webhooks, or load-test the system.
- Review-track validation recorded successful `pnpm typecheck`, lint, and targeted tests. A broader test run recorded 50 passing files/312 tests and one database-dependent test file with 11 `ECONNREFUSED` failures because no MySQL listener was available. These results do not establish production behavior.
- Deployment facts remain unverified, including SAML enablement and IdP assignment, Cloudflare/origin topology, TLS behavior, proxy trust, rate-limit settings, multi-node operation, object-store policy, backup recipients, SharePoint permissions, alert delivery, and branch-protection settings.
- The findings describe evidenced weaknesses and plausible preconditions. They do not assert confirmed exploitation or absolute insecurity.

## 3. Benchmarks and decision criteria

The report used OWASP ASVS as the application-verification baseline, with the OWASP authentication, session, SAML, CSRF, headers/CSP, TLS, file-upload, cryptographic-storage, logging, and API guidance as implementation-oriented benchmarks.[^asvs][^auth][^session][^saml][^csrf][^headers][^upload][^logging][^api] NIST guidance informs authenticator throttling/recovery, federation, key lifecycle, incident logging, contingency planning, and secure software development expectations.[^nist63b][^nist63c][^nistkey][^nistlog][^nistcp][^ssdf]

For a public release, the minimum decision criteria are:

1. No reachable High-severity issue remains without an approved, tested mitigation or feature disablement.
2. High-risk workflows are tested against production-equivalent dependencies, including MySQL concurrency behavior, Stripe test mode, object storage, IdP, and reverse proxy/CDN.
3. Deployment-dependent controls are demonstrated rather than inferred from documentation.
4. Recovery, audit evidence, monitoring, and escalation work independently of the portal being healthy.
5. The promoted artifact, its dependencies, and its source revision are immutable and verifiable.

## 4. Confirmed strengths that should be preserved

The following controls were **confirmed in reviewed source/configuration** and should remain protected during remediation:

- Browser sessions use an `HttpOnly`, production-`Secure`, `SameSite=Strict`, `__Host-`-prefixed cookie. JWT issuer/audience/algorithm checks are paired with authoritative server-side session, user-status, idle-timeout, and absolute-expiry checks (`server/auth/session.ts`).
- Protected procedures apply server-side checks for incomplete MFA, restricted users, forced password changes, required policy acceptance, email verification when enabled, and separate staff/admin role authorization (`server/trpc/trpc.ts`).
- Local password processing uses Argon2id; magic-link and reset secrets are CSPRNG-generated, hashed, expiry-bounded, and magic-link redemption uses a conditional single-use update (`server/security/crypto.ts`, `server/routers/auth.ts`).
- The application uses a fresh CSP nonce with `strict-dynamic`, restrictive source directives, `frame-ancestors 'none'`, `base-uri 'none'`, and related browser headers; HTML shells are marked `no-store` (`server/security/headers.ts`, `server/app.ts`).
- Sensitive fields use AES-256-GCM with record-bound AAD; email lookup uses a separately keyed HMAC blind index. TOTP secrets and SharePoint credentials/tokens are encrypted at rest (`server/security/crypto.ts`, `server/auth/mfa.ts`, `server/services/sharepointDelegatedAuth.ts`).
- Uploads have baseline authentication/CSRF controls, bounded multipart limits, type/magic checks, opaque keys, and no-store attachment delivery (`server/http/uploads.ts`, `server/services/storage.ts`, `server/http/downloads.ts`).
- Nginx and the primary `readypackets.service` have substantial hardening: fail-closed host handling, TLS 1.2/1.3 configuration, request limits, a dedicated non-login service account, filesystem/device isolation, capability removal, and resource controls (`deploy/nginx.conf`, `deploy/readypackets.service`).
- The repository has meaningful recovery scaffolding: scheduled backup invocation, archive structural checks, restore member/path validation, controller boundaries, and a documented recognition that the default pattern is single-node (`deploy/backup.sh`, `deploy/restore.sh`, `docs/GLOBAL_SCALE_ARCHITECTURE.md`).

### Required observability and incident-response operating model

Before public launch, the operating model should be implemented and exercised as follows:

1. **Evidence pipeline.** Emit allowlisted structured security/activity events to an independently administered collector over authenticated encrypted transport. Preserve an immutable retention tier, monitor collector delivery, and record tamper-evident checkpoints. Routine portal administrators and application database identities must not be able to alter retained evidence.
2. **Alert policy.** Define severity thresholds, named primary/secondary owners, acknowledgement and escalation SLOs, after-hours coverage, deduplication, and a delivery-failure alert. At minimum, page on authentication anomalies, privileged configuration/restore events, scheduler/worker failures, backup failure or staleness, storage/database outage, certificate risk, queue backlog, disk exhaustion, origin/WAF attack signals, and audit-sink failure.
3. **Privacy-by-design logging.** Persist only typed, purpose-limited fields. Exclude credentials, tokens, session artifacts, message bodies, arbitrary request bodies, customer file contents, and unnecessary provider-error text. Pseudonymize or time-limit IP-derived values where they are genuinely necessary. Apply the same sanitization before durable storage and every SIEM format/export.
4. **Monitoring separation.** Use external multi-location liveness, authenticated user-journey, and restricted dependency-readiness probes. Do not expose diagnostic internals on a public health endpoint. Record database pool/connectivity, storage checks, worker heartbeat and queue age, backup freshness/remote-copy state, memory/CPU/disk/files, TLS expiry, and rate/WAF anomalies in dashboards with documented SLOs.
5. **Exercises.** Run a staged alert drill for a synthetic security event and a scheduler/backup failure, then an incident/restore tabletop using independently retained logs. Measure detection, notification, acknowledgement, containment, evidence preservation, recovery, communications, and follow-up ownership.

### Verification quality rules

- Execute tests with **production-equivalent versions and topology**, but without production secrets or customer data.
- Test concurrency against the target database engine/configuration, not an in-memory substitute.
- Treat source-level unit tests as necessary but insufficient for IdP, Stripe, object storage, CDN/WAF, egress, mail, certificate, and systemd behavior.
- Retain test logs, immutable artifact identity, configuration redacted of secrets, dates, environment, pass/fail result, and responsible approver in a restricted evidence repository.
- Re-test fixed code through the actual deployment path; a local passing test does not validate a CDN/proxy, firewall, system service, or external provider control.

## 11. Release decision and exception policy

### Decision

**Decision: Block public internet publication for this revision.** The portal may not be approved for a public production decision until the High findings in Section 5.1 are closed, gated features are disabled with evidence, or leadership accepts a documented exception that includes all of the following:

- explicit scope, affected data/users, preconditions, and business justification;
- security-owner, system-owner, and executive approval;
- compensating controls that are already deployed and independently verified;
- a fixed expiry date, remediation owner, tracking identifier, and rollback/feature-disablement plan;
- confirmation that the exception does not bypass legal, contractual, privacy, or regulatory obligations; and
- re-evaluation before expiry and after any material architecture/dependency change.

An exception cannot substitute for the mandatory recovery, edge-origin, immutable evidence, deployment, and release-provenance evidence needed to operate an internet-facing portal responsibly.

### Conditions for reconsideration

A release review should be reconvened only after the go-live checklist has evidence for every applicable item, the consolidated register is updated with closure references, and a final independent-network acceptance confirms that no reachable High-severity finding remains. The reassessment should state the deployment topology and feature scope actually approved (for example, whether SAML, SharePoint synchronization, generic webhooks, S3, Cloudflare, and single-node operation are enabled).
